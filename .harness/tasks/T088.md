## Overview
Regression follow-up to the now-merged T080 + T081. After autoplay was moved out of SessionViewModel.init()/grade() into a single CanvasPaneView `.task(id: currentNote?.id)` trigger (T081, commit 5bc263b), Listen-and-Write mode no longer auto-plays the card's pronunciation on-device — the user must tap the speaker. Listen SHOULD still auto-play automatically; the only change T080/T081 wanted was TIMING (fire once the writing card has actually loaded/appeared, not synchronously in init/grade and not never). Trace must still never auto-play (keep T080), Translate must still never auto-play, and the 'Audio autoplay' setting must still be respected.

Confirmed wiring: triggerAutoplayOnCardAppearance() (SessionViewModel.swift:413) early-returns unless `presentedMode == .listen` (plus `!hasAutoplayed` and `autoplayEnabled`); hasAutoplayed resets on advance (SessionViewModel.swift:271 in grade(), :292 in advanceFreeStudy()). The ONLY caller is CanvasPaneView.swift:42. CanvasPaneView renders inside SessionView, presented via a `.fullScreenCover` in HomeView (HomeView.swift:80-124), so the pane mounts behind the cover's entrance animation.

Confirmed root cause (two problems converge on 'silent'): (1) the single `.task(id:)` is the entire mechanism and is UNTESTED — the green tests (SessionViewModelTests.swift:356 testListenModeAutoplaysAudioOnEntryAndOnAdvance etc.) all call triggerAutoplayOnCardAppearance() DIRECTLY with presentedMode already resolved to .listen and hasAutoplayed already false, so they never exercise the real appearance path, the fullScreenCover entrance transition, or new-card mode resolution — they mask the regression and stay green while the device is silent; (2) for a NEW card, ModeResolver.nextMode() (Scheduler/ModeResolver.swift) returns .trace BEFORE the sessionMode branch (`if cardState == .new { return .trace }`), so a Listen session that opens on a new card can never satisfy the `presentedMode == .listen` guard. The user wants autoplay tied specifically to 'after the load/transition animation completed', which the current bare `.task` does not guarantee.

## Do
In the Session feature ONLY (SessionViewModel / CanvasPaneView / SessionView), make Listen-mode autoplay fire reliably once the writing card has appeared and its entrance/transition has settled, and add a regression test that would have caught the current masked wiring.

1. Make the appearance trigger robust and settle-aware. Keep the design where the VIEW drives autoplay after the card is on screen (do NOT move it back into init()/grade() — that was the T080/T081 point). In CanvasPaneView / SessionView, ensure triggerAutoplayOnCardAppearance() is invoked after presentedMode is resolved AND after the writing card has actually appeared and its load/transition animation has settled — e.g. drive it from the view once the card is on screen with a short post-appearance hook rather than synchronously on bare mount, so it lands after the fullScreenCover entrance transition rather than during it. It must fire once per card on first appearance AND again per advance (after the next card is drawn), matching the hasAutoplayed reset points. Keep the accessibilityIdentifier/UI query surface unchanged.
2. Keep the VM guard semantics but make them survive the real path. triggerAutoplayOnCardAppearance() must still: fire only in Listen (presentedMode == .listen), never in Trace, never in Translate, respect autoplayEnabled, and fire at most once per card (hasAutoplayed). Do NOT weaken the Trace/Translate exclusions.
3. If the fix requires the trigger to survive a new card resolving to .trace (new cards resolve to .trace even in a Listen session), do NOT change new-card behaviour — new cards legitimately show Trace and should not autoplay. Only ensure that REVIEW/relearning cards in a Listen session autoplay as before.
4. Add a regression unit test to Tests/UnitTests/SessionViewModelTests.swift that reproduces the ordering/coverage gap: drive the REAL first-card appearance path for a Listen session on a review card (presentedMode resolved to .listen by init, hasAutoplayed false) and assert exactly ONE autoplay fires for that first card, and exactly one MORE after advancing to the next card (total 2) — using the scripted FakeAudioPlayer, an in-memory SwiftData container, and the injected AppClock. The test must assert the count precisely (not >=1) so a never-fires regression AND a double-fire both fail it. Ensure this test would FAIL on today's masked wiring path and PASS after the fix.
5. Do not touch anything outside the listed scope. Regenerate is handled by the harness; run the full DoD (SwiftFormat --lint, SwiftLint --strict, xcodebuild test on Kakitori-Sim) before finishing.
